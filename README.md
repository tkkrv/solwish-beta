# SolWish (beta)

> Flowers fade. SolWish stays.
> Zero-fee P2P gifting on Solana: wishlists, gift links and greeting cards that live on-chain forever.

**Status:** public beta on **Solana Devnet**. The Colosseum submission build lives in a separate repository/deployment and is not affected by this beta.

## What it does

| Product | How it works |
| --- | --- |
| **Wishlist** (`/create` → `/w/<id>`) | Set a goal in SOL and share one link. Friends gift from a connected wallet, from a phone via Solana Pay QR, or right inside X as a **Solana Blink**. Progress and the wall of greeting cards are read **directly from the blockchain**. |
| **Gift link** (`/gift` → `/claim#…`) | TipLink-style: a one-time wallet is generated in the browser, funded with SOL + a card, and its key travels in the URL fragment (never sent to a server). The recipient claims to any wallet in one tap. |
| **Greeting card** (`/card/<signature>`) | A shareable card verified against the transaction: amount, sender name and message from SPL Memo. |

## How it uses Solana

Every gift is a single atomic transaction:

1. `ComputeBudgetProgram.setComputeUnitLimit` — SPL Memo costs roughly 300–400 CU per byte, so long Cyrillic cards get headroom (no priority fee is added).
2. `SystemProgram.transfer` — SOL goes straight from the giver to the recipient. SolWish never holds funds.
3. `SPL Memo v2` — a compact JSON card:

```json
{ "app": "SolWish", "v": 1, "wishId": "wish_k3j9x2m1p0qa", "from": "Azamat", "msg": "Happy birthday!" }
```

The wishlist page finds gifts with `getSignaturesForAddress(recipient)`, filters memos by `app` + `wishId`, and sums the transfers. The database only stores the wishlist itself.

Blinks: `actions.json` maps `/w/*` → `/api/actions/gift/*` (and legacy `/blink?id=` links). The Action GET returns one-click amounts derived from the goal plus a form with `{amount}`, `{senderName}` and `{message}` parameters.

## Tech

Next.js 16 (App Router), React 19, Tailwind CSS 3, `@solana/web3.js` 1.x, Solana Wallet Adapter (Phantom, Solflare + Wallet Standard), `@solana/actions`, Supabase (Postgres), zod, Solana Pay transfer requests, `next/og` for share images. UI in Russian, Kazakh and English.

## Run locally

Requirements: Node.js 20+, a Supabase project, a wallet (Phantom/Solflare) switched to **Devnet**, test SOL from <https://faucet.solana.com>.

```bash
npm install
cp .env.example .env.local     # fill in Supabase URL + service_role key
npm run dev                    # http://localhost:3000
```

Database: run [`supabase/migrations/0001_wishes.sql`](supabase/migrations/0001_wishes.sql) in the Supabase SQL editor. It creates the `wishes` table and enables Row Level Security (public read, writes only through the server API).

Checks:

```bash
npm run typecheck
npm run lint
npm run build
```


## Security notes

- The recipient address always comes from the database; URL parameters cannot redirect a gift.
- All inputs are validated on the server (zod): amounts, addresses (on-curve only), string and memo byte limits, https-only cover URLs.
- The browser never talks to Supabase directly; the service-role key stays on the server.
- Gift-link keys live only in the URL fragment and in the creator's browser (`localStorage`, for the "My links" list and refunds).
- Rate limiting is in-memory (per instance). Use Upstash/Vercel KV before mainnet.
